## 2. S1-016 requirements and acceptance criteria

The implementation should reject an input unless all required information is valid. It must cover:

1. Missing target name.
2. Empty target name.
3. Whitespace-only target name.
4. Target name longer than 120 characters.
5. Missing source URL.
6. Empty or whitespace-only source URL.
7. Malformed or relative URL.
8. Protocol other than HTTP or HTTPS.
9. URL outside the confirmed supported platform.
10. Valid target input succeeds.
11. Valid values are trimmed before being returned.
12. Nulls, numbers, arrays, and malformed objects are rejected safely.

Additional acceptance conditions:

- Validation is reusable from both browser and server code.
- The server remains authoritative.
- Successful validation returns normalized, strongly typed data.
- Failures return deterministic codes and safe field-level messages.
- Supported-host matching must resist deceptive hostnames.
- Validation performs no HTTP requests, scraping, redirect following, DNS lookup, or provider calls.
- Tests are deterministic and do not require credentials or network access.
- A future endpoint must return validation failures as HTTP 400 and must validate before persistence.

Because the professor’s requirement is stronger than the issue wording, unsupported-platform URLs should be rejected rather than treated as an optional check.

## 4. Conflicting or missing requirements

These require a team decision:

1. **Provider conflict:** S1-001 says the review provider is pending; S1-002 fixes the UI to Google Maps.

2. **Hostname rules are unspecified:** S1-002 says accepted Google Maps hostnames belong in the schema but does not list them. The team must decide among formats such as:
   - `www.google.com/maps/...`
   - `maps.google.com/...`
   - `maps.app.goo.gl/...`
   - Legacy `goo.gl/maps/...`
   - Country-specific Google domains

3. **Path requirements:** An exact Google hostname alone may not prove the URL is a Maps URL. Accepted path rules must be confirmed.

4. **Short links:** They can be recognized syntactically, but their final destination cannot be verified without following redirects—which is explicitly out of scope.

5. **Field contract:** No implementation currently establishes whether the input property is `name`, `targetName`, or `entityName`.

6. **Platform input:** S1-015 allows the platform to be fixed. I recommend that the server assign the single supported platform rather than trust a browser-supplied platform value.

7. **HTTP wording:** Validation permits both HTTP and HTTPS, while the malformed-URL message tells users to begin with `https://`. The proposed behavior is to accept both protocols while retaining the approved message.

8. **URL length:** No maximum is specified. I would not invent one without team approval.

9. **Character counting:** I recommend counting user-visible Unicode code points for the 120-character name limit, consistent with PostgreSQL character-length behavior.

10. **Unknown properties:** I recommend returning only allowlisted validated fields and never propagating `ownerId` or `userId`. Whether all other unknown properties should be rejected or ignored should be aligned with S1-015.

## 5. Recommended interfaces and result structure

Subject to coordination with S1-014, I recommend:

```ts
export const SUPPORTED_REVIEW_PLATFORM = "google_maps" as const;

export type SupportedReviewPlatform = typeof SUPPORTED_REVIEW_PLATFORM;

export interface ValidatedAnalysisTargetInput {
  name: string;
  sourceUrl: string;
  platform: SupportedReviewPlatform;
}

export type AnalysisTargetInputField = "name" | "sourceUrl";

export type AnalysisTargetValidationErrorCode =
  | "INVALID_INPUT_TYPE"
  | "TARGET_NAME_REQUIRED"
  | "TARGET_NAME_INVALID_TYPE"
  | "TARGET_NAME_TOO_LONG"
  | "SOURCE_URL_REQUIRED"
  | "SOURCE_URL_INVALID_TYPE"
  | "SOURCE_URL_MALFORMED"
  | "SOURCE_URL_UNSUPPORTED_PROTOCOL"
  | "SOURCE_URL_UNSUPPORTED_PLATFORM";

export interface AnalysisTargetValidationIssue {
  field?: AnalysisTargetInputField;
  code: AnalysisTargetValidationErrorCode;
  message: string;
}

export type AnalysisTargetValidationResult =
  | {
      success: true;
      data: ValidatedAnalysisTargetInput;
    }
  | {
      success: false;
      error: {
        code: "INVALID_ANALYSIS_TARGET_INPUT";
        message: string;
        issues: readonly AnalysisTargetValidationIssue[];
      };
    };

export function validateAnalysisTargetInput(
  input: unknown,
```

## 8. Security risks and mitigations

- **Hostname spoofing:** Use parsed `hostname` equality against an explicit allowlist, never `includes`, `endsWith` without a dot boundary, or raw-string substring matching.

- **Homograph domains:** Rely on normalized parsed hostname and an explicit ASCII allowlist.
- **Ownership forgery:** Never accept or return browser-supplied `ownerId` or `userId` as authenticated ownership.
- **SSRF misconception:** Format validation is not sufficient SSRF protection. Future ingestion code must separately control outbound requests and redirects.
- **External side effects:** The validator will make no network or provider calls.
- **Information leakage:** Return fixed safe messages without stack traces, parser exceptions, credentials, or provider details.
- **Resource abuse:** Enforce the name bound; a URL-size bound should be added only after the team specifies one.
- **Prototype or malformed input:** Validate the top-level shape and field types before accessing string methods.
